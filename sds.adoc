== 2. ภาพรวมสถาปัตยกรรมระบบ (System Architecture Overview)

=== 2.1 แนวทางสถาปัตยกรรม
ระบบออกแบบเป็นสถาปัตยกรรมแบบ Client-Server บน Framework สมัยใหม่ ประกอบด้วย:

* *Frontend / Application Layer:* Next.js (App Router), React, TypeScript
* *Backend / Database Layer:* Supabase (PostgreSQL) เข้าถึงผ่าน Prisma ORM
* *AI Layer:* Google Gemini API และ DeepSeek API สำหรับสร้างและแนะนำสูตรอาหาร
* *Validation Layer:* Zod สำหรับตรวจสอบความถูกต้องของข้อมูลก่อนบันทึกลงฐานข้อมูล
* * Testing Layer:* Jest สำหรับ Unit Test และ Integration Test ของ Business Logic, API และ Utility Functions

=== 2.2 รูปแบบการออกแบบ (Design Pattern)
ระบบใช้แนวคิด *Recommender System แบบผสมผสาน (Hybrid)* ร่วมกับ *Generative AI*
เพื่อประมวลผลข้อมูลวัตถุดิบและพฤติกรรมผู้ใช้ (ประวัติการค้นหา การกดถูกใจ และคะแนนรีวิว)
ในการคัดเลือกและสร้างสูตรอาหารที่เหมาะสมกับผู้ใช้แต่ละราย

== 4. การออกแบบส่วนประกอบระบบ (Component Design)

=== 4.1 โมดูลจัดการผู้ใช้ (User Management Module)
*Input:* email, password, username, avatar URL
*Output:* session token, user profile data
*Dependencies:* Supabase Auth (cookie-based SSR)
*API endpoints:*
* `POST /api/auth/register` — ลงทะเบียน
* `POST /api/auth/login` — เข้าสู่ระบบ
* `POST /api/auth/logout` — ออกจากระบบ
* `GET /api/users/me` — ดูโปรไฟล์
* `PATCH /api/users/me` — แก้ไขโปรไฟล์
* `DELETE /api/users/me` — ลบบัญชี (cascade)

=== 4.2 โมดูล AI สร้างและแนะนำสูตรอาหาร (AI Recipe Generation & Recommendation Module)
*Input:* รายการวัตถุดิบที่ผู้ใช้มี (optionally quantity/unit), user context (allergies, favorites)
*Output:* JSON recipe object {name, ingredients_needed, steps[], serving_size}
*Dependencies:* Google Gemini API, DeepSeek API
*Flow:*
. รับรายการวัตถุดิบจากผู้ใช้
. เรียก `buildIngredientPrompt()` → สร้าง prompt คำสั่ง
. ส่ง prompt ไปยัง AI API (Gemini หรือ DeepSeek)
. parse response JSON และส่งกลับให้ frontend
*API endpoints:*
* `GET /api/ai` — สร้างสูตรอาหารจากวัตถุดิบที่ระบุ
*หมายเหตุ:* ยังไม่ใช้ Vercel AI SDK `streamText()` — ใช้ raw SDK โดยตรง (Phase 4)

=== 4.3 โมดูลรีวิวและให้คะแนน (Review & Rating Module)
*Input:* recipe_id, rating (1-5), comment (optional)
*Output:* review object + updated recipe average rating
*Dependencies:* Prisma (transaction: insert review + update recipe avg_rating)
*Flow:*
. ตรวจสอบสิทธิ์ผู้ใช้ (ต้อง login)
. ตรวจสอบความถูกต้องด้วย Zod schema (รวม `recipe_id`)
. insert review + recalc `avg_rating` และ `review_count` ของ recipe
*API endpoints:*
* `POST /api/reviews` — สร้างรีวิว
* `PATCH /api/reviews/[id]` — แก้ไขรีวิว (เจ้าของเท่านั้น)
* `DELETE /api/reviews/[id]` — ลบรีวิว (เจ้าของเท่านั้น)
* `POST /api/reviews/[id]/like` — toggle ถูกใจรีวิว

=== 4.4 โมดูลตรวจสอบข้อมูล (Validation Module)
*Input:* ข้อมูลจาก request body (JSON)
*Output:* ข้อมูลที่ผ่านการ validate แล้ว หรือ ValidationError
*Dependencies:* Zod schemas
*Schemas ที่มีอยู่:*
* `auth` — register, login validation
* `recipe` — create/update recipe validation
* `ingredient` — create/update ingredient validation
* `search` — search query validation
* `review` — create review validation (มี `recipe_id`)

=== 4.5 โมดูลจัดการรายการโปรด (Favorite Module)
*Input:* recipe_id
*Output:* toggle state + favorite count
*Dependencies:* Prisma (upsert / delete)
*API endpoints:*
* `POST /api/favorites` — toggle ถูกใจ/เลิกถูกใจ
* `GET /api/favorites` — รายการสูตรที่ผู้ใช้ถูกใจ

== 5. ข้อกำหนดที่ไม่ใช่หน้าที่การทำงาน (Non-functional Requirements)

=== 5.1 ประสิทธิภาพ (Performance)
* API response time เฉลี่ย < 500ms (ไม่รวม AI generation)
* AI recipe generation < 10 seconds (with timeout fallback)
* Page load (SSR) < 2 seconds (First Contentful Paint)

=== 5.2 ความสามารถในการขยาย (Scalability)
* ฐานข้อมูล PostgreSQL ผ่าน Supabase รองรับ Row-Level Security สำหรับ multi-tenant
* API routes เป็นแบบ stateless — สามารถ scale horizontally ได้
* AI API calls ใช้ fallback ระหว่าง Gemini และ DeepSeek เพื่อลด single-provider risk

=== 5.3 ความพร้อมใช้งาน (Availability)
* Supabase SLA 99.9%
* AI API failure → return error message ให้ผู้ใช้ทราบ พร้อม suggestion ให้ลองใหม่
* Graceful degradation: เมื่อ AI ล้มเหลว ระบบยังคงแสดงสูตรอาหารที่มีอยู่ได้

=== 5.4 การบำรุงรักษา (Maintainability)
* โค้ด TypeScript ทั้ง project — type-safe
* Prisma schema-first — เปลี่ยน schema แล้ว auto-migrate
* Zod validation — logic ตรวจสอบอยู่ที่เดียว ไม่กระจายใน route handlers
* ESLint + Prettier — consistent code style

'''

== 6. การออกแบบการรักษาความปลอดภัย (Security Design)

=== 6.1 การยืนยันตัวตน (Authentication)
* Supabase SSR Auth — cookie-based session (httpOnly, secure, sameSite)
* ใช้ `supabase.auth.getUser()` เสมอ (verify token กับ Supabase ทุก request)
* ห้ามใช้ `getSession()` (อ่านจาก cookie ฝั่ง client ไม่ปลอดภัย)
* Session timeout ตามค่าเริ่มต้นของ Supabase (3600 วินาที)

=== 6.2 การควบคุมสิทธิ์ (Authorization - RBAC)
* Role: `USER`, `STORE`, `ADMIN`
* USER: ดูสูตร, สร้างสูตร, รีวิว, ถูกใจ
* STORE: เผยแพร่วัตถุดิบ + role-based ingredient management
* ADMIN: จัดการผู้ใช้ทั้งหมด, ดู audit trail
* ตรวจสอบ ownership ใน route handlers (เช่น แก้ไขรีวิวได้เฉพาะเจ้าของ)

=== 6.3 การตรวจสอบข้อมูล (Input Validation)
* Zod Schema validation ก่อนทุก operation ที่เขียนข้อมูล
* Error format มาตรฐาน: `{error: string, details?: ZodError[]}`
* HTTP status codes: 400 (validation), 401 (unauthorized), 403 (forbidden), 404 (not found), 409 (conflict)

=== 6.4 การเข้ารหัสข้อมูล (Data Encryption)
* Data in transit: HTTPS (TLS) — Next.js + Supabase
* Data at rest: Supabase PostgreSQL encryption ตามมาตรฐาน
* Password: Supabase Auth handles hashing (bcrypt) — ไม่ต้อง implement เอง
* ไม่เก็บ secrets/api keys ในโค้ด — ใช้ environment variables (`process.env`)

'''

   สูตรอาหารจาก AI ตามวัตถุดิบที่มี, แก้ไขโปรไฟล์
2. *ร้านค้า* — เผยแพร่ข้อมูลวัตถุดิบที่ต้องการระบายก่อนหมดอายุ, จัดการส่วนลด

== 11. แนวทางการทดสอบระบบ (Testing Strategy)

=== 11.1 ระดับการทดสอบ (Testing Levels)
|===
| ระดับ | เครื่องมือ | ขอบเขต | สิ่งที่ทดสอบ

| Unit Test
| Jest
| Validation Schemas, Utility Functions, Business Logic
| ตรวจสอบ Validation, Role Mapping, Duplicate Detection และฟังก์ชันที่ทำงานแยกส่วน

| Integration Test
| Jest
| Server Actions, API Routes, Service Layer
| ตรวจสอบการทำงานร่วมกันระหว่าง Validation, Authentication, Prisma และ Business Logic โดยใช้ Mock Dependencies

| Component Test
| Jest + React Testing Library
| React Components
| Rendering, User Interaction
|===

=== 11.2 แนวทางปฏิบัติ (Practices)
* ใช้ Jest เป็น Framework หลักสำหรับการทดสอบ
* แยก Unit Test และ Integration Test ออกจากกัน
* Mock External Dependencies เช่น Supabase Auth, Prisma Client และ AI APIs ด้วย Jest
* ทดสอบ Validation ผ่าน Zod Schema
* ทดสอบ Business Logic แบบแยกส่วนโดยไม่พึ่งฐานข้อมูล
* ทดสอบ Server Actions และ API Routes ด้วย Mock Dependencies
* รัน Jest Test Suite ผ่าน GitHub Actions ก่อน Deploy
* ตั้งเป้าหมาย Code Coverage มากกว่า 70%

=== 11.3 Test Scenarios หลัก
• ตรวจสอบ Validation ของข้อมูลสมัครสมาชิก
• ตรวจสอบการกำหนด Role ของผู้ใช้
• ตรวจสอบการตรวจจับ Email และ Username ซ้ำ
• ตรวจสอบการสมัครสมาชิกสำเร็จ
• ตรวจสอบการจัดการเมื่อ Supabase ส่งข้อผิดพลาด
• ตรวจสอบการจัดการเมื่อ Prisma บันทึกข้อมูลล้มเหลว
• ตรวจสอบการตอบสนองเมื่อข้อมูลไม่ถูกต้อง
• ตรวจสอบการทำงานของ Server Action สำหรับการสมัครสมาชิก
